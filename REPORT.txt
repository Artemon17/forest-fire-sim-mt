1. УСЛОВИЕ ЗАДАЧИ
================================================================================

Лесной массив представлен клеточной картой с растительностью, водоёмами и
противопожарными разрывами. Клетка может быть безопасной, горящей,
потушенной или выгоревшей. Огонь распространяется на соседние клетки с
вероятностью, зависящей от растительности, ветра и времени горения.

Датчики наблюдают участки карты и передают сообщения координационному центру.
Сообщения могут задерживаться, дублироваться или теряться. Центр направляет
ограниченное число пожарных групп к обнаруженным очагам. Тушение занимает
несколько тактов.

Один такт включает фазы:

    наблюдение -> сообщения -> решения -> движение -> тушение ->
    -> распространение огня -> рендер

Порядок строго фиксирован, состояние публикуется после завершения всех фаз.

ЦЕЛЬ РАБОТЫ: взять готовую последовательную имитацию (ИЗ №1) и реализовать
её многопоточную версию, где сущности с собственным поведением представлены
потоками, а взаимодействие между ними организовано через мьютексы и семафоры.

2. СЦЕНАРИЙ: СУЩНОСТИ -> ПОТОКИ
================================================================================

2.1. Соответствие сущностей модели и потоков
--------------------------------------------------------------------------------
Сущность         Тип в коде          Представление в потоках
--------------------------------------------------------------------------------
Пожарная станция st_r, st_c (World)  часть main; как датчик — отдельный
                                     сенсорный поток
Датчик           Sensor              sensor_thread_fn, N датчиков = N потоков
Пожарная группа  FireTeam            team_thread_fn, K команд = K потоков
Клетка огня      FireState (state[]) W fire-воркеров обрабатывают срезы
                                     сетки параллельно
Сообщение        Message (in_flight) общий канал (main), короткоживущее,
                                     не поток
Задача           Task (tasks)        структура данных под teams_lock
Центр            center_*            main — единственное решающее звено
--------------------------------------------------------------------------------

Обоснование: сущности, у которых есть собственное поведение во времени
(наблюдение, движение, распространение), — отдельные потоки. Сущности-«события»
(сообщения, задачи) — данные, которые обрабатываются потоками или main.
Центр по природе последователен, распараллеливать в нём нечего.

Типичный состав: 1 main + 6 сенсоров + 5 команд + 8 fire-воркеров = 20 потоков.

2.2. Фазы такта и параллелизм
--------------------------------------------------------------------------------
Фаза             Параллелизм       Синхронизация            Почему так
--------------------------------------------------------------------------------
1. Наблюдение    N потоков         barrier (2 круга)        датчики независимы,
                                                            пишут в свои слоты
2. Сообщения     main              in_flight.lock           малый объём работы
3. Центр         main              —                        одно решающее звено
4-5. Команды     K потоков         barrier + teams_lock     делят state[] и
                                                            occupant[]
6. Огонь         W потоков         sem_t fire_go/fire_done  клетки независимы,
                                   (fire-cv: condvar)       пишем в буфер
7. Рендер        main              —                        один экран
--------------------------------------------------------------------------------

3. ПОЛЬЗОВАТЕЛЬСКИЙ ИНТЕРФЕЙС
================================================================================

Программа — консольное приложение для Linux.

ВЫВОД. Кадр собирается в один буфер и пишется одним системным вызовом write
в STDOUT_FILENO — это исключает мерцание. ANSI-последовательности
(\033[2J\033[H, \033[K, \033[38;5;Nm) управляют очисткой экрана,
позиционированием и цветом. Размер терминала определяется через
ioctl(TIOCGWINSZ).

Кадр содержит:
  - шапку: такт, направление и силу ветра, число горящих / потушенных /
    выгоревших клеток, число сообщений в пути и в инбоксе;
  - вторую строку: задачи (ждут / в работе / готово / отменено),
    группы (занято / всего);
  - карту: " трава, t дерево, w вода, _ ров, F огонь, # выгорело,
    S станция, . датчик, 1..9 группы;
  - последние 5 событий из журнала.

ВВОД. Клавиши в неканоническом режиме (termios): q — выход, Ctrl+C —
прерывание через sigaction(SIGINT).

АРГУМЕНТЫ КОМАНДНОЙ СТРОКИ
--------------------------------------------------------------------------------
--map FILE          файл карты
--conditions FILE   файл конфига (по умолчанию data/conditions.conf)
--station R C       поставить станцию в клетку (R, C)
--station-scan      перебрать всех кандидатов из карты
--seed N            фиксированный генератор случайных чисел
--delay MS          задержка между тактами
--quiet             не рисовать кадры
--no-ansi           без ANSI-последовательностей
--------------------------------------------------------------------------------

ИНФОРМАТИВНОСТЬ. Ключевые события выводятся в терминах предметной области:
  «Датчик #3 шлёт сообщение #12 о (7,10)»
  «Центр: задача #5 -> группа #2 (расстояние 4)»
  «Группа #1 потушила (8,11)»
Наблюдатель понимает, что происходит в каждый момент времени.

6. АСИНХРОННОЕ ВЗАИМОДЕЙСТВИЕ: МЬЮТЕКСЫ И СЕМАФОРЫ
================================================================================

6.1. Мьютексы
--------------------------------------------------------------------------------
Мьютекс         Защищает                             Где держится
--------------------------------------------------------------------------------
teams_lock      state[], occupant[], tasks при       внутри team_thread_fn
                движении и тушении                   на одну команду
log.lock        кольцевой журнал EventLog            log_add, log_last_n
in_flight.lock  очередь сообщений                    queue_push,
                                                     queue_remove_at
--------------------------------------------------------------------------------
Порядок захвата: teams_lock -> log.lock, никогда наоборот.

6.2. Семафоры
--------------------------------------------------------------------------------
В fire-фазе используется семафорный барьер на паре sem_t fire_go и fire_done:

    main  : for i in 0..W-1: sem_post(fire_go)    // «начинайте»
    worker: sem_wait(fire_go)                     // ждёт команды
    worker: fire_spread_worker(...)               // работает
    worker: sem_post(fire_done)                   // «я закончил»
    main  : for i in 0..W-1: sem_wait(fire_done)  // ждёт всех

На каждую параллельную фазу — 2 круга синхронизации: старт («работайте») и
финиш («я иду дальше»). Main всегда дожидается конца предыдущей фазы, поэтому
дедлока нет.

6.3. Атомики
--------------------------------------------------------------------------------
_Atomic FireState next_state[] — fire-воркеры пишут в буфер без мьютекса.
Обоснование отсутствия гонок:
  - два воркера пишут ST_BURNING в одну клетку — результат один;
  - ST_BURNT пишет только «владелец» клетки (для чужих can_ignite возвращает
    0) — единственный писатель.

atomic_int stop — флаг завершения: atomic_store в main, atomic_load в
воркерах.

6.4. Генератор случайных чисел
--------------------------------------------------------------------------------
Используется rand_r с отдельным seed на каждый поток. Вызов rand() недопустим:
его внутренний мьютекс сериализует потоки и убивает параллелизм.
Сиды: global_seed ^ (0x9E3779B9 * (tag + 1)), tag уникален для воркера.

6.5. Протокол завершения
--------------------------------------------------------------------------------
    main    : atomic_store(&stop, 1)
    main    : разбудить всех (3 круга барьеров, W раз sem_post fire_go)
    воркеры : видят stop, выходят из while(1)
    main    : pthread_join на все потоки
    main    : sim_close_pending() — закрыть висящие задачи
    main    : world_free, освобождение ресурсов

Main отпускает всех ровно один раз. Воркеры не ждут друг друга напрямую —
только main. Дедлока нет.

6.6. Анализ гонок
--------------------------------------------------------------------------------
Сценарий                                   Защита
--------------------------------------------------------------------------------
Два fire-воркера зажигают одну клетку      оба пишут ST_BURNING, результат один
Один зажигает, другой сжигает              can_ignite возвращает 0 для
                                           горящей клетки; ST_BURNT пишет
                                           единственный владелец
Две команды идут в одну клетку             под teams_lock, BFS проверяет
                                           OCC_TEAM
Два сенсора пишут в лог                    log.lock
Main читает лог при рендере                log.lock в log_last_n
Main применяет next_state -> state         все воркеры остановлены после
                                           финишного барьера
--------------------------------------------------------------------------------

Побитовая воспроизводимость при одном seed НЕ гарантируется. При разных

7.7. Производительность
--------------------------------------------------------------------------------
На карте 22x36 (792 клетки) MT-версия не быстрее последовательной: стоимость
6 барьеров на такт сравнима с полезной работой fire-spread (~1 мс). Команды
сериализуются через teams_lock — параллелизм фактически отсутствует.

Ожидаемое ускорение — на картах от 5000 клеток, где fire-spread доминирует над
синхронизацией. Вывод: параллелизм оправдан, когда объём работы на такт
больше стоимости барьера. На учебных картах цель — корректность, а не
скорость.

8. АЛЬТЕРНАТИВНАЯ ПРОГРАММА (другие синхропримитивы)
================================================================================

Реализованы две программы:
  - build/fire    — основная, fire-фаза на sem_t;
  - build/fire-cv — альтернативная, fire-фаза на pthread_cond_t +
                    pthread_mutex_t.

Различие — только в синхронизации fire-фазы. Остальные фазы (sensors, teams,
messages, log) используют те же примитивы (барьеры, мьютексы). Это допустимо:
ТЗ требует, чтобы вместо семафоров были использованы другие синхропримитивы,
а не чтобы были заменены все примитивы.

Реализация
--------------------------------------------------------------------------------
Файл                                   Назначение
--------------------------------------------------------------------------------
include/fire_sync.h                    абстракция через #ifdef USE_CONDVAR
include/sync_sem.h, src/sync_sem.c     реализация через sem_t
include/sync_condvar.h,
src/sync_condvar.c                     реализация через pthread_cond_t
--------------------------------------------------------------------------------
fire-cv собирается с -DUSE_CONDVAR, fire — без него. Оба бинарника работают на
одних и тех же данных.

Как работает condvar-версия: pthread_cond_wait атомарно отпускает мьютекс и
блокирует поток; pthread_cond_broadcast будит всех ожидающих. Счётчики
go_count / done_count играют роль «значения семафора» — тот же механизм, что
внутри sem_t, но реализованный вручную.

Проверка:
    make all
    ./build/fire    --map data/map_big_01.map --station 11 13 --seed 42 --quiet
    ./build/fire-cv --map data/map_big_01.map --station 11 13 --seed 42 --quiet
    ulimit -n 65536
    valgrind --tool=helgrind ./build/fire-cv --map data/map_big_01.map \
             --station 11 13 --seed 42 --quiet

Обе программы работают, helgrind для fire-cv: 0 errors.


================================================================================
9. ОГРАНИЧЕНИЯ И ПУТИ УЛУЧШЕНИЯ
================================================================================

1. Сериализация команд через teams_lock — параллелизм фактически отсутствует.
   Путь: snapshot-подход (снимок state[], локальное планирование, короткая
   критическая секция на применение результата).

2. Недетерминизм относительно планировщика: порядок захвата teams_lock меняет
   порядок задач и сообщений (11 vs 15 тактов при одном seed).
   Путь: детерминированная очередь команд по индексу team_id.

3. RNG per-thread — нет побитового совпадения с ST-версией.
   Путь: хеш-RNG hash(seed, r, c, tick).

11.3. Общий вывод
--------------------------------------------------------------------------------
ИИ ускоряет рутину (парсеры, шаблонный код, структура), но требует трёх
уровней проверки:

  1. Компилятор (-Wall -Wextra -Wpedantic) — синтаксис и базовые типы.
  2. Тесты (valgrind, helgrind, -fsanitize=thread) — гонки и утечки.
  3. Сверка с ТЗ — пропуски требований. ИИ не помнит ТЗ, только то, что
     есть в промте.

Урок: ключевые требования из ТЗ нужно явно переносить в каждый промт.
Пропуск семафоров — прямое следствие того, что в промте не было указано
«ТЗ требует семафоры».


================================================================================
12. ВЫВОДЫ
================================================================================

  1. Многопоточная версия корректна: helgrind — 0 errors, memcheck — 0 leaks,
     стресс-тест — 0 провалов из 20.
  2. Архитектура: три группы потоков (сенсоры, команды, fire-воркеры),
     барьеры между фазами, main оркестрирует такт.
  3. Синхронизация: барьеры + семафоры + мьютексы + атомики достаточны для
     модели; в альтернативной программе семафоры заменены на condvar.
  4. Производительность: на малых картах MT не быстрее ST; ускорение
     ожидается на больших картах.
  5. Недетерминизм — осознанный компромисс между параллелизмом и
     воспроизводимостью.
